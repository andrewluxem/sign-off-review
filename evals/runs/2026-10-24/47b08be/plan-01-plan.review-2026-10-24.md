# Sign-off review: plan-01-plan.md, profile build-plan, stage 3
**Verdict:** Return
**In one line:** No, a fresh agent cannot run this safely: step 3 depends on a schema agreed only in an earlier conversation, steps 4 and 6 give no connection details, and step 5 deletes the only copy of the archive with no backup and no completeness check.
**Question:** Can a fresh agent with shell access on gazette-app-1 carry out this migration safely? (given)
**Answer the draft gives:** Implicitly yes: six steps (stop `archive-web`, export to `/tmp/archive.jsonl`, create the schema, load, `rm /srv/archive/archive.db`, set `DATABASE_URL` and restart), done when "The archive homepage loads."
**Assumptions:** Profile `build-plan` was detected from the numbered steps, commands, paths and done-when, and not confirmed because the user could not be asked. Stage 3 (final) by default. The draft never states its answer to the question, so the answer above is read from the steps. All five seats ran as parallel subagents; no seat ran inline.

## Missing outside view
- "about 9 GB" for archive.db (Context): no measurement, command or date behind it. The disk and outage decisions rest on it; covered by findings 5 and 9.
- Size of the JSONL export in step 2: no estimate from a sample export; covered by finding 9.

## Premortem
1. Step 3 stalls because the schema exists only in the earlier conversation, so the executor, with `archive-web` already stopped, invents tables that `archive-load` or `archive-web` reject, or halts and leaves the public archive offline. (internal)
2. The executor's shell on gazette-app-1 has no credentials or network path to gazette-db-1, so step 4 fails after the outage has begun and the agent loosens access or reuses a privileged role to push the load through. (internal)
3. The archive data is larger or messier than assumed, the `/tmp` export truncates or the load skips rows, step 5 deletes archive.db, and the homepage still renders, so the loss surfaces weeks later when an editor cannot find an old issue.

## What is good and must survive
- Step 1 stops `archive-web` before the export, so the web service cannot change archive.db mid-export.
- Each step is a literal command (`systemctl`, `archive-export`, `archive-load`) rather than prose, which gives exact actions to wrap with checks.
- The Context section names the host, service, file path, size and database host in one place (gazette-app-1, `archive-web`, `/srv/archive/archive.db`, about 9 GB, gazette-db-1), so each claim is easy to verify once discovery commands are added.
- The goal names who benefits and why: "so editors can run reports without copying the file."
- No secret, password or credentialed connection string is written into the plan.

## What fixed looks like
Step 3 applies a named, versioned schema file with a pasteable command and cites where the layout was decided. One `DATABASE_URL`, defined before step 3 with a fill rule for each part and a named secret source, serves both the load and the site. archive.db is backed up and the backup verified before step 1, a gate after step 4 compares per-table counts between SQLite and Postgres and halts on any mismatch, and the delete happens only after a verified cutover and the owner's go-ahead. With those three Blockers closed the verdict moves to Release with fixes; closing the Majors (failure branches and rollback, pre-flight checks, pasteable commands, a checkable done-when, a named owner, disk, downtime, security, other writers and scope) moves it to Release.
