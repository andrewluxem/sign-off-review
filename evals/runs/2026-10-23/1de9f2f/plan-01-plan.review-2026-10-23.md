# Sign-off review: plan-01-plan.md, profile build-plan, stage 3
**Verdict:** Return
**In one line:** A fresh agent cannot run this safely: step 3 depends on a schema that exists only in chat, the plan never says how to connect to Postgres, and step 5 deletes the only copy of the archive before anything checks the load.
**Question:** Can a fresh agent with shell access on gazette-app-1 carry out this migration safely? (given)
**Answer the draft gives:** Implicitly yes: six numbered steps (stop the site, export to JSONL, create the schema, load, delete archive.db, set DATABASE_URL and restart) presented as ready to run, done when "The archive homepage loads."
**Assumptions:** Profile `build-plan` detected from the numbered steps, commands, paths and done-when, not confirmed with the user. Stage 3 (final) by default. "Fresh agent" read as an agent with no chat history and only this document, with a shell on gazette-app-1 and sudo rights unknown.

## Premortem
1. The agent stops archive-web at step 1, reaches step 3 and finds no schema, because "the table layout we agreed on earlier" lives only in chat; it invents one or stalls, and the public archive stays down with no stop rule and no way back. (internal)
2. The export or load in steps 2 to 4 comes up short (a truncated export, rejected rows, the wrong target database), nothing checks it, and step 5 deletes `/srv/archive/archive.db`, the only copy of every issue since 2014. (internal)
3. The data is larger or messier than "about 9 GB" suggests, so the export fills the filesystem holding `/tmp` on gazette-app-1 or runs far longer than anyone planned, and the outage has no deadline that triggers a rollback.

## What is good and must survive
- The Context section introduces the source path `/srv/archive/archive.db`, its size, the archive-web service, both hosts and the Postgres version before the steps use them.
- Each step that has a command gives it literally in backticks, so its outcome can be checked.
- Step 1 stops archive-web before the export, so the export is taken while the site is not writing to the SQLite file.
- The goal ties the work to a real need: "so editors can run reports without copying the file".
- The plan writes no credential or connection string into the document; the fixes for findings 3 and 11 must name where secrets live, not paste them.

## What fixed looks like
The schema sits in the plan or at a named DDL path under a decision ID. Every connection detail (host, port, database, role, credential location, the DATABASE_URL line) is named and set before the step that needs it. A preflight before step 1 confirms access, free space, the archive-web build and the Context facts, and stops on any failure. archive.db is backed up and verified before anything changes, and its deletion has left this run for a post-sign-off move to a retention path. Each state-changing step has a failure signal, a stop rule and a rollback to SQLite. The done-when proves the site reads Postgres with matching row counts, and a named owner receives a defined report.
