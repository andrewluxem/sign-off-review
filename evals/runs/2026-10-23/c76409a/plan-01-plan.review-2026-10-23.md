# Sign-off review: plan-01-plan.md, profile build-plan, stage 3
**Verdict:** Return
**In one line:** No: the plan deletes the only copy of the archive before anything checks the load, and a fresh agent cannot carry out step 3 (a schema "agreed on earlier") or steps 4 and 6 (no database, role, credential or `DATABASE_URL` value).
**Question:** Can a fresh agent with shell access on gazette-app-1 carry out this migration safely? (given)
**Answer the draft gives:** Implicitly yes: six steps stop `archive-web`, export to `/tmp/archive.jsonl`, create the schema, load Postgres, delete `/srv/archive/archive.db` and restart on `DATABASE_URL`, done when "The archive homepage loads."
**Assumptions:** Profile `build-plan` and stage 3 (final) were detected from the draft's numbered commands, paths and done-when, and could not be confirmed with the user. The executor is taken to have only this document and shell access on `gazette-app-1`, as the question states. The five seats ran as independent subagents, each given only its own section of the profile.

None.

## Missing outside view
- Archive size, "about 9 GB" (Context): no measurement or date is given for it, and the free-space requirement for the export rests on it. Raised in finding 7.
- Outage length for steps 1 to 6: no estimate, and no past run or trial load on a copy to base one on. Raised in finding 8.
- Size of `/tmp/archive.jsonl` and the time to load it into Postgres: neither is measured or estimated. Raised in findings 7 and 8.

## Premortem
1. The agent reaches step 3 with the public site already down, finds no record of "the table layout we agreed on earlier", and either invents a schema that `archive-load` maps wrongly or leaves the archive offline while it waits for someone to answer. (internal)
2. The export truncates when `/tmp` fills, or `archive-load` stops partway, the homepage still loads from the partial data, and step 5 has already removed `/srv/archive/archive.db`, so the missing issues cannot be recovered. (internal)
3. `gazette-db-1` refuses connections from `gazette-app-1`, or the deployed `archive-web` build cannot serve from Postgres, so the cutover fails at step 4 or step 6 with the site down.

## What is good and must survive
- Step 1 stops `archive-web` before the export, so the export is a consistent snapshot.
- Each action step is an exact command against named paths and the systemd unit (`archive-web`, `/srv/archive/archive.db`, `/etc/archive/env`), not a description.
- The Context section introduces both hosts, the database path, its approximate size and the Postgres version before the steps use them.
- No secret, password or connection string is written into the plan.
- The one-line goal ties the migration to an editor outcome, which gives the done-when something to test against.

## What fixed looks like
A fresh agent with only this document and shell access on `gazette-app-1` can run it end to end without guessing. The schema comes from a named file or inline DDL with a decision ID. The target database, roles, credential source and exact `DATABASE_URL` line are stated before the first step that uses them. A pre-flight block, run before the site stops, confirms the tools' flags, Postgres reachability, the `archive-web` build's Postgres support and free disk space, and says to stop if any check fails. `archive.db` is backed up and the backup is verified before anything changes. The deletion comes last, after row counts match and the done-when checks pass, and only with the named owner's go-ahead. Every step has a stop rule, and the rollback to SQLite is written out.
